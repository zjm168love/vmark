① 常见的错误理解

✗ 流水线模型(误导)
planner → spec-guardian → impact-analyst → implementer → auditor → ...

暗示 agent 之间直接传递 context,上游产出自动流到下游。 这是错的 —— subagent 之间的 context 是完全隔离的。

真实拓扑

✓ 中心-辐射模型
主 Claude(orchestrator)
↙   ↓   ↓   ↓   ↘
planner
spec-guardian
impact-analyst
implementer
auditor
每个 subagent = 一次性、无记忆的沙箱会话

主 Claude 是「记忆中转站」

subagent 之间互不通讯,全部回到主 Claude。主 Claude 负责把上游产出重打包塞进下游 prompt:

主 Claude 调 impact-analyst   → 收回影响图(文本)
    ↓
主 Claude 把这段文本记在自己 context 里
    ↓
主 Claude 调 implementer      → 在 prompt 里显式塞进影响图
    "Work Item: XXX
     Impacted files (from impact-analyst): [a.ts, b.ts, c.ts]
     Constraints: TDD, no commits, files <300 lines"

这一点在 implementer.md 里写死了:

## Delegation
Provide subagents with:
  - the Work Item text (goal + non-goals + acceptance)
  - impacted file list (from impact-analyst)   ← 必须主动喂进去
  - explicit constraints (TDD, no commits, ...)

为什么这么设计?

.claude/rules/60-ai-governance.md 第 8 条:

每个前沿模型超过 ~300k token 就会退化(Chroma 2025)。 对于啰嗦任务(search、audit、research),派 subagent 而不是 让主线程累积 context。

隔离不是 bug,是 feature:

  • impact-analyst 跑完释放 context — 主 Claude 只留它的最终结论(几百 token),不留它 grep 翻文件的几万 token 噪音
  • implementer 拿到的是被「蒸馏」过的输入,不会被 spec-guardian 的 checklist、planner 的 ADR 干扰
  • implementer 自己也会再开 sub-subagent 处理批量重命名等脏活,保持自己 context 清爽
一句话:没有「agent 之间直接传 context」这回事。主 Claude 是唯一的记忆载体和调度中枢,所有信息都靠它在 prompt 里手动转译塞给下一个 subagent —— 这既是必须的(沙箱隔离),也是有意的(避免 context 退化)。

② 触发器:谁按下第一个按钮

整个系统的入口只有 5 种,其余所有 agent 之间的「触发」都是 orchestrator 主动调 Task 工具,不是事件。

入口触发条件本质
1. Slash 命令 /feature-workflow、/fix-issue #123、/bump 等 用户按键 → 文件内容被作为 prompt 注入主 Claude
2. Cron 定时 claude-audit.yml:6 cron: "0 9 * * *" —— 修 bug 链
claude-cost-report.yml:6 cron: "0 12 * * *" —— 账本结算 		GitHub 调度器,真正「无人值守」的源头(两条独立 cron)
3. 事件链 workflow_run(audit 跑完续上)/ issues 标签 第一推动力还是 cron 或人开 issue
4. PR push pull_request: [opened, synchronize] git push
5. 手动按钮 workflow_dispatch,GitHub Actions 页面 人点按钮

内部派遣:入口触发的总是主 Claude。它通过 Task 工具读 .claude/agents/*.md,在隔离沙箱里起一个 subagent —— 不是事件,是主动调函数。

术语澄清:本文档里的「Task 工具」是派遣 subagent 的工具,Claude Code 新版本里改名叫 Agent(同一个东西,旧名沿用)。 别和 TaskCreate/TaskUpdate/TaskList 混淆 —— 后者是本会话 TODO 列表的管理工具,跟 subagent 无关。

③ 无人值守链:每天自动修 bug 的完整路径

从 cron 到 PR auto-merge,基于实际文件核对:

1. Claude session(audit) 工具: Bash,Read,Glob,Grep,WebSearch,WebFetch --max-turns 120 ↓ agent 自行用 Bash 调 5. gh issue create 按 5 段式模板批量建 audit 标签 issue ↓ workflow_run 事件(bot 建的 issue 不触发 issues 事件,这里兜底) 6. claude.yml audit-collect job 取 ≤6 个 open audit issue,跳过 fix-attempted ↓ 输出 matrix 7. audit-fix job max-parallel: 3(6 排队、3 并行) ↓ 每个 runner 启动 8. Claude session(fix) 工具: Bash Read Write Edit Glob Grep MultiEdit --max-turns 50 ↓ agent 调 Edit 9. PreToolUse hook ❓ 仓库文件无法证实 CI 是否加载 .claude/settings.json ↓ agent 调 10. gh pr create PR 打开,触发 pull_request 事件 ↓ 同一个 audit-fix job 继续 11. 主校验 session(inline) claude.yml:219-249 工具: Bash Read Glob Grep,--max-turns 10 输出 VERIFIED / NOT VERIFIED / PARTIAL ↓ 校验通过 12. gh pr merge --auto --squash claude.yml:257,等 CI 绿后 GitHub 自动 merge ↓ 若主校验未跑(外部 PAT 创建的 PR 等) 13. audit-verify standalone job(fallback) claude.yml:261-313,只在 fallback 路径生效

✓ 真正的「按钮」只有第 1 步的 cron。 ? 第 9 步存疑(取决于 claude-code-action@v1 实现)。其他 12 步可从仓库文件证实。

并行的另一条 cron:成本结算(无 LLM 参与)

12:00 UTC(audit 跑完 3 小时后)claude-cost-report.yml 独立启动:

A. GitHub cron daemon claude-cost-report.yml:6 cron: "0 12 * * *" ↓ B. checkout ref: data 账本在孤立分支 data,不污染 main ↓ C. 读 .github/cost-reports/ledger.json 汇总过去 24h 所有 Claude bot 的 token / $$ ↓ D. 关掉昨天的 cost-report issue 滚动更新,不留旧 issue ↓ E. 开新 cost-report issue + 数据写回 data 分支

和修 bug 链的差异:纯 shell + gh CLI,不调 Claude、不派 subagent。 时间故意错开 3 小时,等当日 audit-fix 把账本写完再统计。 从 agent 编排角度看是「监控旁路」,但确实是仓库里的第二条无人值守 cron。

④ 本地 vs CI 的触发差异

维度本地 Claude CodeGHA Claude session
入口 slash 命令 / 自由对话 cron / workflow_run / pull_request / issues / workflow_dispatch
Orchestrator 本机 Claude Code CLI 进程 runner 上的 anthropics/claude-code-action@v1
派遣 subagent Task 工具读 .claude/agents/*,起隔离沙箱 单次 prompt 注入,不调 Task,跑完即退
工具集 agent frontmatter tools: 字段决定 workflow 的 --allowedTools 收窄:
• audit: Bash,Read,Glob,Grep,WebSearch,WebFetch
• fix: Bash Read Write Edit Glob Grep MultiEdit
• verify: Bash Read Glob Grep
PreToolUse hook ✓ 生效(gha-tdd-guard.mjs 等) ? 无法从仓库文件证实
轮次上限 无硬性 max-turns(用户随时打断) --max-turns 硬上限:audit 120 / fix 50 / verify 10 / review 15
失败兜底 用户接管 给 issue 打 fix-attempted 标签,下次自动跳过(防死循环)
commit / merge release-steward 等用户说 commit gh pr merge --auto --squash,CI 绿后 GitHub 自动 merge
并发控制 单进程,串行 concurrency.group + max-parallel: 3
一句话差异:本地是「用户驱动 + 多 subagent 编排 + 本地 hook 兜底」,CI 是「事件驱动 + 单段 prompt + workflow 步骤兜底」。两者共享 .claude/agents/* 和 .claude/rules/* 文本(checkout 后都在 runner 里),但执行模型完全不同 —— 本地 orchestrator 反复调 Task,CI 一次性 prompt 跑完就退出。

⑤ Action 与鉴权:CI 怎么调到 Claude

启动方式:本质等价于 claude -p

anthropics/claude-code-action@v1 在 runner 里做的事拆开看就是:

# 1. 装 Claude Code CLI(npm install -g @anthropic-ai/claude-code)
# 2. 用 OAuth token 鉴权
# 3. 用 -p / --print 模式跑 prompt:
claude -p "<workflow yaml 里 prompt: 块的全部内容>" \
       --model opus \
       --max-turns 120 \
       --allowed-tools "Bash,Read,Glob,Grep,WebSearch,WebFetch"

关键特征:

  • -p 模式 = 一次性、非交互、stdout 给结果就退出(对应「CI 上单段 prompt 跑完即退」)
  • workflow yaml 里 prompt: | 块整段被传给 -p 后面
  • claude_args: 里的所有参数原封不动透传给 claude CLI

claude-code-action 是什么:GitHub Action,不是插件

概念在哪例子
GitHub Action 公开仓库 / Marketplace,workflow 触发时临时拉取 anthropics/claude-code-action、actions/checkout
Claude Code CLI npm 包,runner 上临时装 @anthropic-ai/claude-code
Claude Code 插件 本机 .claude/plugins/ cc-suite@xiaolai、tdd-guardian@xiaolai

action 是「自动化包装层」,CLI 才是「真正干活的工具」,插件是「CLI 的扩展」 —— 三者不是一回事。每次 workflow 触发,GitHub Actions 从 github.com/anthropics/claude-code-action 仓库拉 v1 tag,在 runner 里 npm install CLI、设环境变量、调 claude -p。

Token 怎么拿、怎么进 Secret

本地一次性操作(前提:已用 Claude Max 或 Pro 订阅登录过):

claude setup-token

命令会走 OAuth 授权流程,终端打印一个长 token(形如 sk-ant-oat01-...),代表你的订阅授权。

放进 GitHub Secrets:

GitHub repo → Settings → Secrets and variables → Actions
→ "New repository secret"
   Name:  CLAUDE_CODE_OAUTH_TOKEN
   Value: sk-ant-oat01-...

名字必须叫 CLAUDE_CODE_OAUTH_TOKEN,因为 workflow 硬编码引用:

claude_code_oauth_token: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}

还需要 PAT_TOKEN:默认 GITHUB_TOKEN 有反递归保护 —— 它创建的 PR/push 不会触发其他 workflow。audit-fix 创建的 PR 必须能再触发 CI 才能 merge,所以必须用 PAT。

为什么 AGENTS.md 还要强调「订阅优先」

看似废话(CI 已经在用订阅了),但规则的作用域不在 CI,在「人」。这条规则覆盖三个工具:

  • Claude Code — 已经在用,但新人不知道有 OAuth
  • Codex CLI(.codex/agents/*.toml 那套)— 也支持 ChatGPT Plus/Pro 订阅
  • Gemini CLI(目前未用,规则覆盖以防未来加)

它防的是 3 种「下意识踩坑」:

  1. 新贡献者本地装工具时默认被引导用 API key(文档先讲 API),不知道有订阅这条路
  2. AI 自己写脚本调 Anthropic API 时下意识用 ANTHROPIC_API_KEY
  3. 未来加新工具时,决策点上有现成的「订阅优先」原则,不用每次重新讨论

成本数字背书:Claude Opus API 约 $15 in / $75 out per MTok,单个 audit-fix 跑 50 轮约 $5-15,每天 6 个 = $30-90/天。订阅:Claude Max $200/月 = 每天 $6.67,额度内不再扣钱。数量级差异,规则就是要避免有人不小心用 API key 模式跑 CI,一晚上烧掉一个月订阅钱。

一句话:CI 用 claude -p 跑非交互模式,claude-code-action 是临时拉取的 GitHub Action 包装层;鉴权靠 CLAUDE_CODE_OAUTH_TOKEN(订阅)+ PAT_TOKEN(绕开默认 token 的反递归保护);「订阅优先」不是描述现状,是约束未来所有新加 AI 工具的默认选择,防止把钱烧在 API 计费上。

⑥ Agent 创建与约束

✗ 直觉理解

workflow 里写了「Plan (Planner agent)」「Implement (Implementer agent)」… 应该有某种 harness 检查机制,保证主 Claude 真的把这几个 agent 都派出去了 —— 没有。

✓ 实际机制:不验过程,验产物

harness 不监控 Task 调用次数,也不强制顺序。 workflow.md 是散文,模型自己读自己派。系统只在 产物 这一层卡:每个 agent 该留下什么文件/代码/标记,缺了就过不去。

每个 agent 的「存在证据」

Agent该产生的产物谁来验
plannerdev-docs/plans/YYYYMMDD-*.md下游 prompt 要引用此文件,缺了模型卡住
impact-analyst影响文件清单(文本)implementer.md 模板把它拼进 prompt,缺了产出不完整
implementer生产代码 + sibling *.test.ts硬 PreToolUse hook(gha-tdd-guard.mjs)拦 Write/Edit,无测试 exit 2
test-runner测试通过 + 覆盖率达标硬 pnpm check:all 阈值挂掉
auditor零 findings硬 Codex 二审循环,3 轮内未清空 → 不发 PR
—(整条链)WI-1.2 出现在 commit 或测试头硬 scripts/check-wi-linkage.sh
—(阶段)Phase DoD硬 scripts/check-gha-phase.sh <N>
release-stewardcommit用户显式说 "commit"(人工闸)

为什么这样设计

如果主 Claude 偷懒、不派 planner 但自己写出等价 plan 文件,workflow 也能跑通 —— 这是 feature,不是 bug。agent 边界存在的目的是 context 隔离(避免 300k 退化),不是流程警察。流程警察的活交给 hook 和脚本,它们不关心「谁写的」,只关心「写没写」。

一句话:没有任何机制直接保证「所有要求的 subagent 都被创建」。 保证的是 产物 —— 每个 agent 该留下的文件/测试/标记,缺了被 PreToolUse hook、 pnpm check:all、DoD 脚本、Codex 二审挡住。 agent 是组织手段,不是合规手段。

⑦ .claude/ 目录解剖 + 三份配置文件

所有「编排」最终都落在文件上,但绝大多数 .claude/* 是给 LLM 看的静态文本 —— 只有 hooks/ 和 settings.json 会被真正执行。

各子目录加载时机

目录谁读何时加载本质
rules/*.md主 Claude + 所有 subagent每次新 session 开机自动注入;subagent 继承同一套(harness 复用 project rules)项目宪法 —— TDD、tokens、shortcuts
agents/*.mdharness调 Task 工具时沙箱画像 —— frontmatter 定 tools/skills
commands/*.md主 Claude用户敲 /feature-workflow整个文件 = 注入主 prompt 的剧本
skills/*/SKILL.md主 Claude按需(描述匹配)领域知识包 —— Tiptap/Tauri/CSS
hooks/*.mjs外部进程每次 Write/Edit 前真正会执行的代码 —— exit 2 即 block

三种信息流转

编排流: 用户 /feature-workflow → harness 把 commands/feature-workflow.md 全文塞进主 Claude → 主 Claude 自觉调 Task(planner) → harness 读 agents/planner.md frontmatter,起隔离沙箱 → planner 文本结果返还主 Claude,主 Claude 手动重打包给下一个 规则流: rules/*.md 不需要调用,会话开机自动进 system prompt → subagent 也继承(harness 复用 project rules) 拦截流: 主 Claude 调 Edit → settings.json 的 PreToolUse 触发 → 跑 hooks/gha-tdd-guard.mjs + multi-format-tdd-guard.mjs → 任一 exit 2 → 工具调用被拒,主 Claude 必须先写测试

三份配置文件分工

文件谁读性质放什么
.claude/settings.json Claude Code CLI 本体 JSON 配置,不进 LLM context 启用哪些插件、注册哪些 hook、权限白名单
CLAUDE.md 主 Claude 会话开机注入 仅 Claude 独有规则;本项目只有一行 @AGENTS.md + 一条「不用 project memory」
AGENTS.md 所有 AI 工具(Claude/Codex/Gemini) 跨工具宪法 编码风格、技术栈、Tauri 桥接、token 规则、auth 优先级

为什么这么分:VMark 用多个 AI 工具 —— Codex CLI、Gemini CLI 都不认 CLAUDE.md,但都认 AGENTS.md(OpenAI 主推的跨工具标准)。CLAUDE.md 只放 Claude 专属备注 + 一行 @AGENTS.md 转发指针,实现单源真相。而 settings.json 是另一个层级 —— 它告诉 CLI 进程怎么工作,主 Claude 只能看到它执行的结果(比如「工具被拒了」)。

插件 vs 本仓库 .claude/

插件不是「另一种东西」,是.claude/ 同类内容的可分发打包。docs-guardian/、tdd-guardian/ 这两个目录里的 JSON 就是插件的「项目级抽屉」 —— 主 Claude 根本不读它们,是插件代码在用。

组件类型放在 .claude/放在插件里有 prompt 吗
Slash 命令commands/*.md插件的 commands/(例: /cc-suite:audit)有 —— 调用时整段注入主 Claude
Subagent 定义agents/*.md插件的 agents/有 —— Agent 工具调用时注入
Skillskills/*/SKILL.md插件的 skills/有 —— description 匹配时注入
Hookhooks/*.mjs插件的 hooks/无 —— 是脚本,不是 prompt
MCP server.mcp.json 里注册插件自带(例: cc-suite 注册 codex-cli)无 —— 提供工具,不是 prompt
持久化状态—.claude/<插件名>/*.json(本项目 docs-guardian/、tdd-guardian/)无 —— 插件代码读写

本仓库三个插件实际侧重(在 settings.json 的 enabledPlugins 里启用):

  • cc-suite@xiaolai —— prompt 型:/cc-suite:audit 等一堆命令 + Codex MCP server,配置在根目录 .cc-suite.md
  • tdd-guardian@xiaolai —— hook + 状态型:gate 状态机存在 .claude/tdd-guardian/state.json
  • docs-guardian@xiaolai —— hook + 映射型:code→doc 对照表存在 .claude/docs-guardian/config.json

真正的区别不是「有没有 prompt」,而是位置和分发:

  • .claude/ 内容 = 跟仓库走(git 提交),只对本项目生效
  • 插件内容 = 装在 ~/.claude/plugins/,跨项目复用,用户得在 settings.json 主动启用

所以「tdd-guardian 插件 vs hooks/gha-tdd-guard.mjs」是两套独立机制:前者是跨项目的 gate 状态机(commit 时查 gate),后者是本项目 hard-coded 的 Write/Edit 拦截器(工具调用时 exit 2)—— 都叫 TDD 守卫,但作用点完全不同。

一句话:.claude/ 90% 是文档,只有 settings.json 和 hooks/ 会被「执行」。文档负责把规则、剧本、角色画像塞进 LLM 的 context;hooks 在工具调用边界做强制拦截。CLAUDE.md → AGENTS.md 是跨工具入口转发,settings.json 是 CLI 本体的工程配置。插件 = 把上面这些做成可跨项目分发的包 —— 启用后,它带的 prompt/hook 按各自机制注入,「有没有 prompt」取决于组件类型,不取决于是不是插件。
